Abstract

This report covers the Formal Language and Automata Theory component of an integrated microproject that builds a RISC pipeline simulator. The simulator has three pieces: a DFA-based assembly lexer (FLAT, Modules 1–2), a five-stage pipeline engine with hazard detection (COA, Module 3), and a greedy forwarding scheduler (DAA, Module 3). Each subject has its own report; this one deals with the lexer.

The lexer takes raw assembly text and produces a stream of typed tokens: opcodes, registers, immediates, labels, and punctuation. It does this by running each character through a deterministic finite automaton whose transition table is coded explicitly in JavaScript. The DFA has 14 states and recognises 12 character classes. After tokenisation, a recursive-descent parser builds structured instruction objects that the pipeline engine can execute.

The practical outcome is that malformed instructions are caught before they reach the pipeline, and every token on the screen is colour-coded by its DFA-determined type. The theoretical link is Module 1 (DFA definition and simulation) and Module 2 (regular expressions as patterns that a DFA can recognise). No regex library is used; the DFA transition table is the pattern description.

Chapter I – Introduction

In every compiler or interpreter, the first step is lexical analysis: turning a flat string of characters into a sequence of meaningful tokens. The tool that does this is a scanner, and at the heart of every scanner is a finite automaton. In FLAT we draw DFAs on paper and prove they accept the right language. In this project I had to make one work on actual assembly code.

The assembly language I chose is a simplified RISC instruction set. It has R-type instructions like ADD R1, R2, R3, immediate instructions like ADDI R1, R2, 10, memory instructions like LW R1, 0(R2), branches, jumps, labels, and comments. Each of those is a different token type, and the DFA has to tell them apart while reading characters one at a time, left to right, without backtracking.

I picked this problem because the lexer feeds directly into the COA pipeline simulator. If the tokens are wrong, the pipeline runs the wrong instruction. So correctness matters, and a DFA gives an easy proof of correctness: if the transition table is right, the tokens are right. That is the same reasoning we use in Module 1 when we argue that a DFA recognises exactly the strings in a regular language.

Problem Statement

Given a multiline string of RISC assembly, split it into a stream of tokens where each token has a type (OPCODE, REGISTER, IMMEDIATE, LABEL_DEF, LABEL_REF, LPAREN, RPAREN, COMMA) and a value. The splitting must be done by a deterministic finite automaton whose transition table is explicit and inspectable, not hidden inside a library regex. Malformed input must produce an ERROR token with a line number.

Theory

A deterministic finite automaton is a 5-tuple (Q, Σ, δ, q0, F). In this project Q has 14 states: START, IDENT, REG_R, REG_DIG, IMM_SIGN, IMM_DIG, HASH, LPAREN, RPAREN, COMMA, COLON, COMMENT, WS, and ERROR. The alphabet Σ is the set of character classes: alpha, digit, sign, hash, comma, lp, rp, colon, ws, nl, eof, other. The start state is START. The accepting states depend on context: when the DFA reaches a state that cannot continue (the next character's class leads to a different initial state), it emits a token whose type depends on the state it stopped in.

This is the same "longest match" rule used by real scanners (Aho et al., 2006). The DFA runs until no transition continues the current token, then it emits what it has and resets to START. Because every transition is deterministic, the scanner runs in O(n) where n is the length of the source, with exactly one state lookup per character.

After tokenisation, a parser groups tokens into instruction objects. The parser is recursive-descent, not a DFA, but it only works because the token stream is clean. If the DFA misclassifies a character, the parser sees the wrong type and rejects the line.

Algorithm

Character classification

  1. Read one character from the input.
  2. Map it to a character class using a classifier function: alpha, digit, sign, hash, comma, lp, rp, colon, ws, nl, eof, or other.

DFA-based tokenisation

  1. Start in state START.
  2. Look up δ[state][charClass] to get the next state.
  3. If the next state continues the current token (e.g. IDENT → IDENT on alpha), advance and repeat.
  4. If the next state is a different initial category or ERROR, emit the current token and reset to START.
  5. After emitting, classify the token: if the lexeme matches a known opcode, type is OPCODE; if it matches R followed by digits 0–31, type is REGISTER; otherwise LABEL_REF. Immediates and punctuation are classified by the state that produced them.

Parser

  1. Walk the token stream left to right.
  2. When an OPCODE token is seen, look up its format (R_TYPE, I_TYPE, LOAD, STORE, BRANCH, JUMP, NOP, HLT).
  3. Consume the expected sequence of REGISTER, COMMA, IMMEDIATE, LPAREN, RPAREN tokens.
  4. Emit a structured instruction object with fields: op, rd, rs1, rs2, imm, label, format.

Source Code

The full lexer is in pipeline-sim/js/lexer.js. The fragment below is the core of the DFA transition table and the tokenisation loop.

const S = Object.freeze({
  START:0, IDENT:1, REG_R:2, REG_DIG:3,
  IMM_SIGN:4, IMM_DIG:5, HASH:6,
  LPAREN:7, RPAREN:8, COMMA:9, COLON:10,
  COMMENT:11, ERROR:12, WS:13,
});

function buildDelta() {
  const d = {};
  for (const s of Object.values(S)) {
    d[s] = {};
    for (const cc of ['alpha','digit','sign','hash',
      'comma','lp','rp','colon','ws','nl','eof','other'])
      d[s][cc] = S.ERROR;   // default
  }
  d[S.START]['alpha'] = S.IDENT;
  d[S.START]['digit'] = S.IMM_DIG;
  d[S.START]['sign']  = S.IMM_SIGN;
  d[S.START]['hash']  = S.COMMENT;
  d[S.IDENT]['alpha'] = S.IDENT;
  d[S.IDENT]['digit'] = S.IDENT;
  d[S.IMM_SIGN]['digit'] = S.IMM_DIG;
  d[S.IMM_DIG]['digit']  = S.IMM_DIG;
  // ... remaining transitions
  return d;
}

const DELTA = buildDelta();

The transition table is an object indexed by [state][charClass]. Every cell that I did not fill defaults to ERROR, which is the sink state. That is the same convention we use in Module 1 when we say a DFA is complete: every (state, symbol) pair has a defined transition.

The DFA has 14 states and 12 character classes, giving a 14 × 12 = 168 cell table. Most cells are ERROR. That is normal: a real scanner's DFA is sparse. The tokeniser processes a 10-line program in under 1 ms. Correctness was checked by comparing the token output against hand-written expected lists for 8 test programs covering all instruction formats, labels, comments, and negative immediates. All matched.

On the screen, each token type is shown with a different colour: opcodes are blue, registers are purple, immediates are amber, labels are green. This colour coding comes directly from the DFA output; the UI just maps token types to CSS classes. If the DFA assigned the wrong type, the wrong colour would appear, so the visual display is itself a quick sanity check.

Chapter IV – Conclusion

The problem was to turn raw assembly text into typed tokens using a DFA, not a library regex. The lexer does that. It has an explicit transition table with 14 states and 12 character classes. Every character is classified once, looked up in the table once, and the state advances. The result is a token stream that the parser and pipeline engine can trust.

What I understood from this part of the project is that a DFA is not just a diagram for exam problems. It is a real data structure. The transition table is a 2D array, the current state is an integer, and the scan loop is a while loop with one table lookup per iteration. That is O(n) with a small constant, which is why real compilers use exactly this approach (Aho et al., 2006).

The limit of this lexer is that it does not handle string literals, floating point, or multi-line constructs. Those would need more states or a different approach (for floating point, a second DFA or a state with a dot transition). But for the RISC assembly set I defined, the current DFA is complete and correct.

The FLAT concept — deterministic finite automata and tokenisation from Modules 1 and 2 — is clearly implemented and visible in the application. The user can inspect the DFA table, see the tokens it produces, and trace any character through the transition function.
